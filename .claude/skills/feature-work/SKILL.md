# feature-work: Issue 駆動の実装フロー

SiiD Web の標準フロー。詳細ルールは `docs/spec/04_workflow.md` を参照。

## 手順

0. **着手前の一括確認（外部素材・制約がからむタスクのみ）**:
   デザインデータ・動画・スプレッドシート等の外部素材を扱うタスクでは、**探索や解析を始める前に**
   次を 1 回の質問（`AskUserQuestion`）でまとめて確認する。ローカルを `find` で探し回らない。
   - **素材の絶対パス**: `~/Downloads` 等を推測で探索しない。Google Drive 上の Office ファイルは
     ダウンロード経由で往復するので、**ローカルパスを先に貰う**
   - **利用可能な制約**: フォントライセンス（Adobe Fonts の契約有無 / Google Fonts 縛り）、
     使ってよい外部サービス、既存実装・ブランドカラーを流用するか無視するか
   - **完了条件**: 何をもって「一致」「完了」とするか（数値基準・チェックリストの所在）

   > 過去の損失（2026-09-06 LP リニューアル）: 素材の所在を推測して探索し訂正され（2 ツール + 1 往復）、
   > さらにフォント特定のため Adobe Fonts 同期フォルダを走査・比較画像を 3 枚生成した末に
   > 「AdobeFonts は契約していない」と判明し、**約 8 ツール呼び出しが丸ごと無駄**になった。
   > 制約は解析より先に聞けば 1 質問で済む。

1. **Issue 確認**: `gh issue view <N>` で目的・完了条件を読む。Issue 本文からリンクされた `docs/spec/` の仕様書を必ず読む
2. **ブランチ作成**: 最新 develop から切る
   ```bash
   git checkout develop && git pull origin develop
   git checkout -b feature/<N>-<slug>
   ```
   種別により `fix/` `docs/` `chore/` プレフィックスを使い分ける
3. **実装**:
   - Figma 参照が必要な場合、ノード ID は `docs/spec/01_project-overview.md` の対応表から特定し、**最小回数**で `get_design_context` を呼ぶ(View シートのレート制限があるため)
   - 既存下層ページ(`/service`, `/community`)の実装パターンと CSS Modules 命名規則(CLAUDE.md 参照)を踏襲する
4. **検証**: `npm run lint && npm run typecheck` を通し、UI 変更は `npm run dev` でブラウザ確認(SP: 〜1279px / PC: 1280px〜 の両方)
5. **コミット & PR**:
   - コミットは `feat:` 等のプレフィックス付き
   - PR は develop 向け、本文冒頭に `Closes #<N>`、変更概要・確認方法・UI 変更ならスクリーンショットを記載
   - **検証の成果物は `docs/reviews/<N>/` に置き**（`README.md` + PC/SP の webp スクショ）、PR 本文から参照する。
     PR 本文には **「未検証の事項」欄を必ず設け**、確かめられなかったこと（例: 予約枠が無く実フォーム未確認）を明記する。
     後から実測したら PR 本文と仕様書の「未確認」記述を実測値で更新する（#72 の形式が手本）
6. **セルフレビュー**: PR 作成後に `/code-review` を実行し、指摘を修正して push
7. **完了報告**: PR URL をユーザーに共有し、**マージはユーザーに委ねる**(自動マージ禁止)

## 相談・ヒアリングで前提が変わったとき

実装を伴わない相談（リリース計画・構成の質問など）でも、**決まったことはその場で仕様書に書く**。
チャットと Issue コメントにしか残さないと、次のセッションは古い仕様書を読んで同じ説明をやり直す。

- 決定事項（例: 「lp-1 は廃止」）と、ユーザーから出た「なぜ？」への回答（例: Cloudflare と Vercel を併用する理由）を、
  該当仕様書の冒頭に日付付きの注記として追記し、実装 PR か docs PR に載せる
- 仕様書を読んで**実装と食い違う記述**を見つけたら、ユーザーへの報告と同時に上記の注記を入れる

> 過去の損失（2026-09-10）: `06_migration.md` が「`/siid/lp-1` は GitHub Pages に残す」前提のまま、
> 実装側は #40 で移植済み・ヒアリングで廃止決定。決定はチャットと #48 のコメントにしか残らなかった。

## 並行ワークツリーでの検証

このリポジトリは `orca/workspaces/siid-web/*` や `.claude/worktrees/*` に複数のワークツリーがあり、
それぞれで dev server や別 AI が動いている。**「自分のコードを見ている」ことを先に確かめる**。

- **新しいワークツリーでは最初に `npm ci`**。無いまま `npm run lint` すると `next: command not found` で 1 往復失う
- **dev server は空いているポートで自分で上げ、その URL だけを見る**:
  ```bash
  lsof -ti tcp:3000 >/dev/null && echo "3000 使用中: $(lsof -p $(lsof -ti tcp:3000 | head -1) | awk '$4=="cwd"{print $NF}')"
  PORT=3100 npm run dev   # 3000 が他ワークツリーのものなら別ポートで
  ```
  2026-09-10 は 3000 番を**別ワークツリーの next-server** が掴んでおり、検証中に「公式スクリプトが読まれている」
  という自分のコードではあり得ない結果が出て、`lsof` で cwd を突き止めるまで 3 ツール使った
- **ページ全体のスクリーンショットは `scripts/lp-career/shoot-fullpage.mjs` を使う**（`SPDIR` で出力先指定）。
  Playwright MCP の `browser_take_screenshot` の `filename` はワークツリー内に保存されず、
  保存先探しに 4 ツール使った（2026-09-10）。MCP はクリック・計測（`browser_evaluate`）用と割り切る

## 長時間の自走（`/goal`）で気をつけること

`/goal` で完了まで一気に走らせるとき、**条件文の書きぶりそのものが事故になる**。

- **達成不能な前提が条件に入っていないか、着手前に確認する**
  「PR をマージしました」のような**ユーザーしか実行できない行為**が条件文に含まれると、
  Stop hook はそれを毎回「未達の条件」として評価し、エージェント側では永久に満たせない。
  ユーザーが *過去形の前提共有* のつもりで書いた一文でも同じことが起きる。
  気づいた時点で、着手前に達成可能な形への言い換えを 1 行で提案する
  （例: 「PR をマージしました」→「PR #66 の完了条件を全て満たし、push まで終わらせる」）。
- **同じ Stop hook 判定が 2 回続いたら、作業を続けずに停止してユーザーへ条件の修正を求める**
  判定理由が前回と同一なら、それは進捗不足ではなく条件文の不備。押し切ろうとしても空転する。

  > 過去の損失（2026-09-06 LP リニューアル）: 条件文が「PRをマージしました。…」で始まっていたため、
  > Stop hook が **計 14 回**「PR がマージされていない」と判定。うち **11 回が最後の 17 分に集中**し、
  > 同じ判定文を繰り返すだけの空転になった。2 回目の同一判定で止めていれば避けられた。

- **`npm run dev` を上げっぱなしにしない**。PSD 解析・スクリーンショット撮影と並走させると
  メモリ不足でバックグラウンドプロセスが kill される（2026-09-06 に発生し、復旧の Monitor もタイムアウト）。
  確認が終わったら止め、必要になったら上げ直す
- **レビュー用サブエージェントには判定をまとめて渡さない**。1 エージェントに
  「15 セクション × PC/SP = 30 判定」を投げてストール（600s 無進捗）で全滅した。
  セクション単位・観点単位に分割し、失敗時の再実行コストを小さく保つ

## デザイン再現タスクで気をつけること

カンプ（PSD / Figma）どおりに作るタスクは、**「合っているかどうか」を何で判定するか**で
結果がほぼ決まる。自動スコアを信じると、合格のまま崩れたものが出来上がる。

- **自動一致率スコアは進捗の目安であって、合否ではない**
  「N/N 合格」を完了報告の根拠にしない。スコアが合格でも、**必ず自分でスクリーンショットを見て**
  文字の重なり・はみ出し・字送り・色の違いを目で確かめる。
  ピクセル差分系の指標は許容幅（±数 px）を持つうえ、文字サイズ・太さ・色の違いを拾えない。

  > 過去の損失（2026-09-08 LP リニューアル）: `check-design.sh` が 15/15 合格を出す一方で、
  > STRENGTH は文字が写真に重なったまま 91% で「合格」していた。

- **代表セクションを早い段階でユーザーに見せ、品質の水準を合わせる**
  全セクションを仕上げてから見せない。最初の 1〜2 セクションが出来た時点で
  スクリーンショットを提示し、「この水準でよいか」を確認する。以降もセクション単位で区切って出す。

  > 過去の損失（2026-09-08 LP リニューアル）: 約 10 時間・74 コミットを自走したあと、
  > ユーザーが初めてブラウザで見て「デザイン通りに再現できていない」「クオリティとしてはイマイチ」となり、
  > **他 AI への引き継ぎに切り替わった**（Issue #68）。途中で 1 回見せていれば方向修正できた。

- **判定用の計測スクリプトを作ったら、使う前に校正する**
  既知の正解 1 件と既知の不正解 1 件に通し、期待どおりの判定が出ることを確かめてから本番に使う。

  > 過去の損失: 彩度で位置を測る手法がカルーセルの色を拾い、**存在しないずれを 4 回追いかけた**。
  > うち 1 回は修正でページ全体を崩した。

- **検証の前に環境をリセットする**
  古い `next start` プロセスが削除済みの `.next` を配信し続け、「本番では CSS が読まれていない」という
  誤診をした。ビルド成果物を作り直したら、**サーバも必ず上げ直す**。
  スクリーンショットは遅延読み込み画像の完了を待ってから撮る（待たずに撮って SP の判定が
  15/15 → 4/15 に反転した）。

## 禁止事項

- develop への直接コミット
- lint / typecheck 未通過でのコミット
- Issue・仕様書を読まずに実装を始めること
- 外部素材の所在をユーザーに聞かずにローカルを探索すること
- ライセンス・利用可否を確認する前に、その素材の解析に時間を使うこと
- 同じ理由の Stop hook 判定を 3 回以上受けてなお、条件文を疑わずに作業を続けること
- 自動一致率スコアだけを根拠に「デザイン再現が完了した」と報告すること
- デザイン再現タスクで、代表セクションをユーザーに見せないまま全セクションを自走で仕上げること
- 判定用の計測スクリプトを校正せずに、その出力を根拠に修正を重ねること
- ヒアリングで決まった前提を、チャットと Issue コメントだけに残して仕様書に書かないこと
- ポートを掴んでいるプロセスの cwd を確かめずに、localhost の表示を自分の変更の検証結果として扱うこと

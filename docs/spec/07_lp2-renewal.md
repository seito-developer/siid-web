## 6. フォント方針

### 6.1 使用不可フォントと代替

デザインには商用フォント(Adobe Fonts 収録書体)が使われているが、**Adobe Creative Cloud を契約していないため使用できない**。
また §2.1 の理由で画像化による再現も不可能。したがって全て無料 Web フォントに置換する。

| 用途 | 原本 | 出現 | 採用フォント | ライセンス |
|------|------|-----|------------|-----------|
| 見出し・CTA・強調 | 筑紫ゴシック H / E | 114 | **Zen Kaku Gothic Antique** 900 / 700 | OFL |
| 本文・カード・FAQ・比較表 | Noto Sans CJK JP | 235 | **Noto Sans JP** 400 / 500 / 700 | OFL |
| 英字セクションラベル | FuturaPT Heavy Oblique | 36 | **Jost** 700 + `font-style: oblique` | OFL |
| STEP ラベル | DIN 2014 | 10 | **Barlow Semi Condensed**(既存 `fonts.ts` に導入済み) | OFL |
| STEP 番号・VOICE 番号 | Avenir / Futura | 22 | **Jost** | OFL |
| 給付金バッジ | 筑紫明朝 | 8 | **Shippori Mincho B1** | OFL |
| STEP 装飾の「0」 | Confiteria Script | 16 | 装飾 1 文字のみ。CSS の擬似要素で描く、もしくは SVG 化 | — |

**選定根拠**: 筑紫ゴシックはオールドスタイルの温かみを意図した人文的書体であり、
同じ設計思想を持つ Zen Kaku Gothic Antique が最も近い。比較検証では M PLUS 1p Black が
太さの面で近かったが、幾何学的な骨格のため字の性格が合わない。

### 6.2 実装上の注意

- 代替フォントは原本と**字面の大きさが異なる**ため、フォントサイズと字送りの微調整が必要。
  PSD レンダリングと実装のスクリーンショットを重ねて詰める。
- Zen Kaku Gothic Antique Black は原本(Heavy)よりわずかに軽い。
- Google Fonts は日本語を `unicode-range` で分割配信するため、見出し用に別ファミリーを
  追加しても実際に読み込まれるのは使用文字のチャンクのみ。パフォーマンス上の問題はない。
- Next.js Font Optimization(`next/font/google`)で読み込み、`fonts.ts` に集約する。

## 8. 画像アセット

### 8.1 書き出し方針

入稿済みの `images/` `webp_x2/` はカルーセル画像のみで、かつ `errors.txt` の通り
書き出しに失敗した分がある。**PSD から再書き出しする。**

```bash
python3 scripts/lp2/psd_tool.py manifest scripts/lp2/assets.manifest.json
```

- 出力先: `public/images/lp-2/`、形式は **WebP**
- **テキストは画像に焼き込まない。** 代替フォントを使う以上(§6)、PSD の文字を
  画像として貼ることはできない。`exclude_kinds: ["type"]` でテキストレイヤーを除いて
  書き出し、文字は実テキストで重ねる
- **スクリーン合成のグローは画像化できない。** 単独で書き出すと黒く潰れるため、
  `exclude` で除いて CSS の影やグラデーションで表現する
- **クリッピングマスク前提のレイヤーは単独で書き出さない。** 100% 透明になる。
  クリップ元を含む親グループごと書き出すこと
- 単純図形(矢印・チェック・区切り線)は **SVG か CSS で実装**する。画像にしない
- ロゴは既存の `public/images/lp-1/siid-logo.svg` / `siid-logo-w.svg` を流用する
  (新デザインでも字形は同じ。PSD 側は等倍ラスターのため Retina で不足する)
- `next/image` を使う(`<img>` は ESLint エラー)

### 8.2 背景アセットは「前景を隠した文書全体の合成」から切り出す

グループ単体の `export` では、そのグループより上に重なるオーバーレイが反映されず
背景の色がカンプとずれる(実測で R チャンネルが 10〜20)。背景は `section-bg` を使う。

```bash
python3 scripts/lp2/psd_tool.py section-bg <PSD> \
    --hide '<前景グループ>' --hide '<前景グループ>/**' \
    --box 0,901,1440,1942 \
    --match-reference tmp/psd-ref/pc/pc2.png \
    --out public/images/lp-2/xxx-bg.webp
```

さらに psd-tools の `composite()` は「全レイヤー表示・無変更」のときだけ Photoshop
埋め込みのプレビューを返し、レイヤーを 1 枚でも隠すと自前の合成に切り替わる。
自前の合成は Photoshop と色が完全には一致しないため、`--match-reference` で
チャンネルごとに線形補正をかける(実測の残差 0.7〜4.1 / 255)。

### 8.3 next/image の品質は既定のままにしない

既定の `quality=75` で再エンコードすると、背景グラデーションの色が 20 程度ずれる
(実測: `#24A6FC` → `#0E9FF7`)。この 1 点だけで INSTRUCTOR の色一致率が
12.9% に落ちていた。`LP2_IMAGE_QUALITY`(90)を全ての画像に指定すること
(同 80.2% に改善)。

### 8.4 背景は PC と SP で別に用意する

SP のカンプは PC の縮小版ではなく別デザインのため、PC の書き出しを引き伸ばすと
背景が合わない。SP の PSD から別途書き出し、`SectionBg` コンポーネントで
メディアクエリにより出し分ける。

```bash
python3 scripts/lp2/psd_tool.py section-bg <SP の PSD> \
    --hide '<前景グループ>' --hide '<前景グループ>/**' --hide-kinds type \
    --box 0,0,750,1473 --match-reference tmp/psd-ref/sp/<PSD 名>.png \
    --out public/images/lp-2/sp/<セクション名>.webp
```

### 8.5 アセットはフェーズごとに追加する

**全アセットを先に洗い出すことはしない。** 何を画像にして何を CSS / SVG で組むかは
セクションを実装しながらでないと決まらないため。

実装フェーズごとに `scripts/lp2/assets.manifest.json` へ追記し、マニフェストを
再実行する。マニフェストが「どの PSD のどのレイヤーから何を書き出したか」の記録に
なるので、入稿データが差し替わっても再現できる。

フェーズ 0 時点では FV と ABOUT の 3 点のみ登録済み。

### 9.1 変換・実装方針

- `.mov` のままでは Web 配信に適さないため **H.264 MP4** に変換する。

```bash
./scripts/lp2/convert-video.sh ~/Downloads/video
```

  変換結果: `fv-pc` 5,291,609B → **1,394,973B**、`fv-sp` 1,628,375B → **938,555B**。
- **WebM(VP9)は生成しない。** 実測で常に MP4 より大きく(PC 2.25MB vs 1.92MB、
  SP 1.53MB vs 1.46MB)、容量が倍になるだけで得るものが無かった。
- `<video autoplay muted loop playsinline>` で背景再生。`muted` と `playsinline` は
  iOS Safari の自動再生に必須。
- `poster` に FV の静止画(WebP)を指定し、動画ロード前の白画面を防ぐ。
- PC / SP で別ファイルのため、`<source media="...">` もしくは JS による出し分け。
  **LCP に直結するため、SP で PC 用を読ませない**こと。
- **PSD の FV 背景は動画の仮置き**(Zoom 画面のスクリーンショット + 顔隠しの絵文字)であり、
  実際の動画とは別カット。実装してはいけない。詳細は
  [`lp2-sections/02-fv.notes.md`](./lp2-sections/02-fv.notes.md)。
- **カンプと実際の FV の見え方が異なることはヒアリングで承認済み**(動画を使う)。
  そのため §13.1 / §13.2 の一致率判定では、**FV のみ動画領域を除いて判定する**。
- `preload="metadata"`。FV は初期表示領域のため遅延ロードはしない。

### 13.1 PC デザイン一致率(横幅 1440px)

ブラウザで**横幅 1440px** のプレビューを表示し、対応する PSD の基準画像と比較する。

```bash
# 基準画像を書き出す(初回のみ)
python3 scripts/lp2/psd_tool.py render ~/Downloads/260902_seitosama/pc --out-dir tmp/psd-ref/pc

# 実装のスクリーンショットと比較する
python3 scripts/lp2/compare.py \
    --reference tmp/psd-ref/pc/pc1.png \
    --actual    tmp/shots/pc1.png \
    --out       tmp/diff/pc1.png
```

`scripts/lp2/compare.py` は **2 つの指標を独立に算出**する。数値は差分を探す補助であり、合否は §13.0 の目視・操作確認で決める。
単一の指標では「わずかな位置ずれの許容」と「色の誤差の検出」を両立できないため
(位置ずれは輪郭に局所的な大きい差、色ずれは全体に小さい差を生む)。

| 指標 | 算出方法 | 合格ライン | 検出できる誤り |
|------|---------|-----------|--------------|
| **構造一致率** | 4px ぼかし後、最大チャンネル差 24 以内の画素の割合 | **85% 以上** | レイアウト・要素の有無・サイズ |
| **色一致率** | 24px ぼかしで高周波を落とし幅 60px に縮小、許容差 8 で比較。**基準画像側で平坦なセル(局所 σ ≤ 20)に限定** | **85% 以上** | 配色・階調 |

> 色一致率を平坦セルに限定しているのは、文字が乗るセルを含めると Photoshop と
> ブラウザで文字のラスタライズが異なるだけで平均色がずれ、配色が正しくても
> 数値が落ちてしまうため。文字の再現度は構造一致率で判定しており、
> 色軸で二重に減点する必要はない。

較正結果(`pc1.psd` を基準にした実測):

| 比較対象 | 構造一致率 | 色一致率 | 判定 |
|---------|-----------|---------|------|
| 完全一致 | 100.00% | 100.00% | 合格 |
| 全体を 3px ずらす | 88.32% | 96.07% | 合格(軽微なずれは許容される) |
| 明度を 6% 上げる | 100.00% | 73.22% | **不合格**(色の誤りを検出) |
| 幅 1200px で撮影 | 99.70% | 96.19% | 合格(撮影幅に依存しない) |
| 別セクション(pc3) | 14.20% | 10.58% | **不合格** |

#### 構造一致率の実際の上限

文字が面積の大きな割合を占めるセクションでは、配置・書体・サイズが正しくても
**82〜85% 程度で頭打ちになる**。Photoshop とブラウザで文字のラスタライズ
(アンチエイリアスの掛かり方)が異なるためで、実装の誤りではない。

ABOUT セクションで検証した結果:
- 最適なずらし量は dx=1 / dy=1(= 位置はほぼ完全に合っている)
- 1:1 で拡大すると書体・太さ・字幅は一致している
- それでも構造一致率は 82% 前後

このため、判定が 82% 前後で止まるセクションについては、差分画像で
「ずれているのが文字の輪郭だけか」を目視で確認したうえで合否を判断する。

- 高さが一致しない場合、短い方をマゼンタで埋めて全体を比較する。**高さのずれは減点対象**。
- 差分ヒートマップ(不一致画素を赤く重ねた画像)を必ず出力し、レビュー時に提示する。
- 終了コードは従来の閾値判定を示す。レビューエージェントはこれだけで品質合格と判定しない。

#### 13.3.1 404 ページの扱い

`(Lp)` ルートグループには `not-found.tsx` が存在せず、404 は `(Main)` 側
(`src/app/(Main)/[...notFound]`)にフォールバックする。LP から共通クロームを持つ
`(Main)` の 404 に飛ぶ挙動が妥当か、レビュー時に確認する。
問題があれば `(Lp)/not-found.tsx` の追加を別途検討する(本フェーズのスコープ外)。

### 13.4 Cookie 同意バナー

GA4 / GTM を設置するため、Cookie 同意バナーを実装する(決定済み)。

- リポジトリに既存実装は無い。**lp-2 用に新規作成する。**
- 同意前は GA4 / GTM を発火させない(Consent Mode もしくは同意後にタグを注入する方式)。
- 同意状態は `localStorage` に保持し、再訪時にバナーを出さない。
- フッターのプライバシーポリシーリンクと併置する。
- `(Lp)/layout.tsx` は lp-1 と共有のため、**バナーは lp-2 のページ側に置き lp-1 に影響させない**。

### 13.5 実装エージェントとレビューエージェントの分離

品質判定を実装者自身に行わせない。以下の体制とする。

```
実装エージェント          レビューエージェント(サブエージェント)
      │
      ├─ 実装
      ├─ §13.1〜13.3 を自己確認
      └─ 完了報告 ─────────▶ 独立してレビュー
                              ├─ §13.1 PC 一致率を検証
                              ├─ §13.2 SP 一致率を検証
                              ├─ §13.3 チェックリストを検証
                              ├─ 不合格項目があれば修正を実施
                              └─ 全項目合格 ─────▶ フェーズ完了
```

- **レビューエージェントは実装エージェントとは別に起動する。** 実装の文脈を引き継がせない
  (自分の書いたコードを自分で評価すると甘くなるため)。
- レビューエージェントは**指摘だけでなく修正まで行う**。
- **レビューエージェントが全項目で合格を出した時点をもってフェーズ完了**とする。
- 不合格が残る場合は完了報告をせず、修正 → 再レビューを繰り返す。

### 15.7 パフォーマンスの実測と残作業(2026-09-07)

`npm run build` + `npm start` の本番ビルドに対して、Playwright で初期ロードの
転送量を、Lighthouse(モバイル模擬)でスコアを実測した。

**計測時の注意(ここで一度誤った結論を出した)**

`next start` のプロセスが残ったままだと、`rm -rf .next` して再ビルドしても
古いプロセスがポートを掴んだまま**削除済みの `.next` を配信し続ける**。
この状態で計測すると、CSS が当たっていないページを測って
「本番では CSS が読まれていない」「LCP が改善した」といった誤った結論になる。
計測の前に必ず `lsof -ti tcp:<port> | xargs -r kill -9` でポートを空けること。

**削減できたもの**

| 施策 | 効果 |
|------|------|
| FV 動画を初期ロードから外す(load 後アイドル時に `src` を入れる) | クリティカルパスから 431KB |
| FV 動画(SP)を 540px 幅 / CRF 36 に再エンコード | 938KB → 431KB |

| LCP 要素(FV ポスター)の `preload` 追加 | 発見待ちを解消 |

初期ロードの転送量は **3.54MB → 2.34MB**。デザイン一致率は本番ビルドに対して
PC 15/15・SP 15/15 で合格を維持している。

**フォントの自前サブセット化(実施済み)**

転送量の 63% を woff2 が占めていたため、`scripts/lp2/subset-fonts.sh` で
lp-2 が実際に使う文字だけの woff2 を書き出し、`public/fonts/lp-2/` から配信している。

| 書体 | next/font 経由 | サブセット |
|------|--------------:|----------:|
| Noto Sans JP(400/500/700/900) | 750KB | 429KB |
| Zen Kaku Gothic Antique(500/700/900) | 333KB | 169KB |
| Shippori Mincho B1(700) | 300KB | 17KB |
| **合計** | **1383KB** | **615KB** |

**lp-1 には手を入れていない。** フォントの実体は「その字形が実際に描画されたとき」に
しか取得されないため、lp-2 のトークン(`--lp2-font-body` など)をサブセット側へ向ける
だけで next/font 側の取得が止まる。`(Lp)/layout.tsx` の登録はそのままで、lp-1 は従来
どおり next/font の Noto Sans JP を使う(実測で確認済み)。

収録文字は「描画済み DOM から採取した文字(アコーディオン展開・タブ切替後を含む)」と
「lp-2 のソース中の文字列リテラルおよび JSX テキスト」の和集合。取りこぼしがあっても
フォールバック(Hiragino Sans / Hiragino Mincho ProN)に落ちるだけで豆腐にはならない。
文字を増やすコピー変更を入れたら `subset-fonts.sh` を回し直すこと。

ライセンスは 3 書体とも SIL Open Font License 1.1 で、Reserved Font Name の指定が
無いためサブセット化と再配布ができる(`public/fonts/lp-2/OFL-*.txt` を同梱)。

**効かなかった施策(記録)**

- **FV で使う書体の preload**: 上記 3 書体(133KB)を preload したら 性能 83 → 67、
  LCP 3.1s → 5.6s と悪化した。LCP 画像と帯域を取り合うため。フォントは
  `font-display: swap` のまま後から差し替わるほうが速い。
- **`lp1.css` を lp-2 から外す**: `* { box-sizing: border-box }` などのリセットが
  含まれ lp-2 もこれに依存しているため、外すと全セクションが崩れる(§末尾)。

**まだ 90 に届いていない分 — 原因は FV の背景動画で確定している**

残るギャップはほぼすべて Speed Index(7.1s)で、その主因は **FV の背景動画**。
Lighthouse の Speed Index は「画面内の見た目がいつ落ち着いたか」を測るため、
ループ再生し続ける動画があると原理的に完了しない。

動画を出さずポスター画像だけにして計測すると次のようになる(実験のみ・未採用):

| | 性能 | FCP | LCP | Speed Index |
|---|---:|---:|---:|---:|
| 現状(動画あり) | 83 | 2.7s | 3.1s | 7.1s |
| 動画を出さない場合 | **89** | 2.7s | 3.1s | **3.6s** |

つまり **90 に届かせるには FV の動画をやめる(または自動再生しない)必要があり、
これはデザインの決定事項**。カンプは動画前提のため、実装側では判断しない。

**決定(2026-09-08): 動画のループ再生を優先し、83 のまま公開する。**
実ユーザー体感に効く LCP 3.1s / TBT 0〜30ms / CLS 0.008 はいずれも良好で、
Speed Index だけが数値上の減点であるため。

あわせて、スクロールで FV が画面外に出たら再生を止める処理を入れた
(`FvVideo.tsx` の IntersectionObserver)。**これは Lighthouse のスコアには
影響しない**(計測中は FV がずっとビューポート内にあるため。実測でも
83 / SI 7.1s のまま)。通り過ぎたあとの CPU・バッテリー消費を抑えるための実装。

なお、これ以外に残っている削減余地は小さい(lp-1 用の Poppins / Barlow 77KB が
lp-2 でも取得されている分など)。実回線・CDN での実測は公開後に行う。

**あわせて見つかった、いま直していないもの**

- `(Lp)/layout.tsx` が読む `lp1.css`(379KB のチャンクではなく 25KB のほう)には
  `* { box-sizing: border-box }` などのリセットが含まれ、**lp-2 もこれに依存している**。
  lp-2 から外そうとすると全セクションが崩れる。リセット部分を共有ファイルに切り出せば
  lp-2 から lp-1 固有の CSS を外せるが、切り出し方の検証が別途必要。


### 15.8 Issue #68 の仕上げ（2026-09-08）

- カンプの実画素に合わせ、ラベルのサイズをセクション別に分けた。背景に含まれる罫線は二重描画しない。
- 見出しのグラデーション、黄／白の強調範囲、本文のサイズ・折り返し、カードと表の位置を修正した。
- PCのCTAは専用画像 `cta-button-pc.webp` を使用する。`export-bg.sh pc-cta-button` でPSDから再生成し、`clean-cta.mjs` が旧文字の影だけを補間する。
- SKILLSはSPの1枚目を初期展開（実際の可視カンプに合わせる）。カードは通常フローで開閉し、後続カードも押し下げる。PCは常時展開し、タグをカンプの列幅で配置する。
- VOICEとFAQは複数件の展開に合わせてセクションの高さを伸ばす。
- RESULTSはPCで見える5枚を描画し、SPの矢印を説明文が遮らないようにした。
- 本文・ヘッダーは375/1440pxの設計幅を基準に同じ比率で拡縮する。768pxでPC表示へ切り替え、1440pxを超える画面では中央配置する。CSSの長さ除算に未対応のブラウザには `CanvasScale` で数値を補う。ピンチズームは制限しない。
- 予約フォームは不透明な白いカード内に置く。外部フォームの高さが変わったらセクションも伸び、見本カレンダーの透け・下端切れを防ぐ。外部サービスの文言・空き日程・実フォームの高さはカンプとの差を許容する。
- 再現性は通し画像と操作で検証する。`LP2_URL=<対象URL> node scripts/lp2/check-layout.mjs` はSKILLS開閉、RESULTS操作、フォーム高さの回帰確認に使用する。
